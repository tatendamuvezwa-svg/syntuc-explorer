# Syntuc Explorer — QR Feedback MVP

## Scope

This branch adds an initial Heritage Expedition Sunset Cruise feedback pilot:

- Public mobile questionnaire at `/feedback`.
- Five original service ratings (Excellent / Good / Fair / Poor).
- Overall experience comment and Yes/No recommendation question.
- Optional name, email, and experience date.
- Server-side validation, a simple in-memory rate limit, and a honeypot field.
- Administrator-only response API and a Guest Feedback tab in the coordinator desk.
- QR code download/print controls and CSV export.

## API

- `POST /api/feedback` — public form submission.
- `GET /api/feedback/responses` — requires an authenticated staff token and the `admin` role.

Feedback is stored in the `heritage_feedback_responses` Firestore collection with a pilot tenant identifier. The public QR page explicitly states that respondents are not verified guests.

## QR code behaviour

The QR image is currently generated by an external QR image service and encodes only the public `/feedback` URL. Do not put private guest details or tokens in the QR code. The QR URL must be tested against the final deployed hostname before printing.

## Required security gate before real guest data

**Do not use this pilot to collect real guest personal information until Firestore security is reviewed and corrected.** The current `firestore.rules` contains a permissive catch-all rule (`allow read, write: if true`) that makes Firestore collections directly accessible to clients. The new server API restricts its response endpoint to administrators, but that does not override permissive direct Firestore access. A rules refactor must be planned against all existing Syntuc collections, or the feedback collection must be moved to a server-only store using properly configured server credentials. Do not assume this PR solves the repository's existing Firestore rules exposure.

Additional pilot limitations:

- Rate limiting is process-local and resets when the server restarts; it is basic abuse reduction, not a production anti-fraud guarantee.
- A public QR code does not verify boarding, identity, or eligibility to review the cruise.
- Feedback comments can contain personal information; the form asks guests not to include sensitive details.
- The external QR image provider receives the public feedback URL when the QR image is requested.

## Security review follow-up — 16 October 2026

The repository-wide Firestore rules currently include explicit permissive rules for several collections and a permissive catch-all for all remaining documents. Firestore allow rules are additive: adding a deny rule for `heritage_feedback_responses` would not override the catch-all allow. The existing server helper in `server/lib/firestore.ts` uses the Firebase client SDK, so the new API cannot bypass Firestore rules using the current helper.

Do not try to secure this one collection by adding a deny-only match while leaving the catch-all in place. The safe next engineering step is a repository-wide data-access inventory and a planned rules migration, with regression tests for every collection currently used by the guest, coordinator, catalogue, reservation, analytics, and media flows. Another viable architecture is to use a server-only Admin SDK for feedback and remove all client-access paths to this collection, but that alone is not enough while the catch-all client permission remains active.

## Security migration update — 16 October 2026

The broad catch-all Firestore allow rule has now been removed on this feature branch, and `heritage_feedback_responses` has an explicit `allow read, write: if false` rule for client SDK access. The feedback API uses the server-side Firebase Admin SDK helper. This means direct client access to the feedback collection is denied by rules, while the server API can access it with the deployed service identity.

**This is not a complete Firestore security remediation.** Existing explicit rules for `reservation_requests`, `reservation_items`, analytics, media, products, guests, guest tokens, guest messages, healthcheck, and deleted records still grant unrestricted client read/write. These need a separate, carefully tested rules migration. Collections without an explicit allow now fail closed, which may expose missing rules or break workflows that rely on direct client SDK access. Regression-test the whole application before deploying these rules.

The repository has not been deployed from this branch. GitHub Actions build/typecheck checks for the latest rules commit must complete successfully, and live Firestore behavior must be verified in a safe preview environment before merge. The server runtime must have Application Default Credentials and IAM access to the configured Firestore database.

## Additional input/export hardening — 16 October 2026

- The feedback API validates the optional experience date as a real calendar date and rejects future dates. Invalid dates are rejected server-side rather than relying only on the browser date input.
- CSV export prefixes formula-leading guest text with an apostrophe before quoting the cell, reducing spreadsheet formula-injection risk when feedback is opened in spreadsheet software.
- Latest GitHub Actions typecheck/build run is pending for these commits; do not treat earlier successful runs as validation of the latest changes.

### Remaining launch blockers

- The rules file still contains permissive client read/write access for multiple non-feedback collections. This PR only isolates the new feedback collection; it is not a full application-wide Firestore security fix.
- Existing server routes use the Firebase client SDK helper for many collections, so tightening those rules without migrating and testing their access paths may break application workflows. A separate repository-wide access inventory and staged migration are required.
- Live Firebase Admin SDK credentials/IAM, persistence, QR scanning, coordinator authorization, and full regression tests have not been verified in a deployed preview.
